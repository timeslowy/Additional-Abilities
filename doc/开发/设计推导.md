# 设计推导与失效分析

> 本文件是**开发文档**，记录 Additional Abilities 若干关键设计背后的推导过程与失效场景。
>
> 源码注释只保留**当前仍然成立的契约与原因**（一两句）。完整的场景推演、反例构造、
> 方案比较与审查过程放在这里，避免把源码变成设计文档。
>
> 阅读顺序建议：先读源码注释了解"必须怎样"，再回到本文件了解"为什么当初要这样"。

---

## 1. 蓄力档位：AUTO 是请求哨兵，不是档位

**背景**：`charged` / `optional_charged` 族系的客户端在松手时发送 `ChargedReleasePayload`，
"请求档位"字段同时承载三种含义：未指定（`AUTO = -1`）、取消（`CANCEL = 0`）、具体档位（`>= 1`）。

**失效**：客户端曾用 `releaseLevel < 1` 判断"这次是取消"。但放手时若玩家没有滚轮选档，
发送的是 `AUTO`（-1），于是**服务端正常释放、扣蓝、进冷却，客户端却走取消分支** ——
预测与结束表现不一致。

**当前契约**：请求哨兵（`AUTO` / `CANCEL`）与解析后的业务档位必须分开表达。
`ChargedCastResult` 只承载业务档位；`ChargedCasting#pendingLevel` 用 `OptionalInt`
区分"未指定"（empty）与"已选定为取消"（0）。

## 2. 蓄力时长：服务端零网络容差

**背景**：服务端复算档位时取三者最小值：

```text
effectiveTicks = min(max(payloadTicks, 0), max(serverCurrentTick, 0), max(castTime, 0))
```

**失效**：若服务端相信客户端上报的 `chargeTicks`（只按 `cast_time` 封顶，不核对真实
`currentTick`），那么"合法开始施法后立即上报 `chargeTicks = cast_time`"就能绕过等待、
直接拿到自身最高档。

**当前契约**：`api.ChargedCasting` 的全部入口一律传服务端自己的
`DragonAbilityInstance#getCurrentTick()`，因此正式入口上不存在"调用方声称蓄了多久"。

## 3. 蓄力终结的四条路径

一次蓄力有四条终结路径，统一结算服务覆盖其中三条：

| 路径 | 是否经过 ChargedCasts |
| --- | --- |
| 手动松手提前释放 | 是（`fire`） |
| 超限窗口到点自动释放 | 是（`settleOvercharged`） |
| 松手时档位不足 / 选定取消 | 是（`settle` 的取消分支） |
| **DS 原生读条完成**（`can_charge_exceed_cast_time = false`） | **否**，走 `SyncStopCast#handleServer` → `MagicData#stopCasting` |

**结论**：选档记录的清理不能挂在各结算分支里，否则第四条路径会漏掉。
必须挂在 `MagicData#stopCasting` 的尾部——那是四条路径的共同漏斗。

**注意**：该注入点在 TAIL，此时 `isCasting` 已被置为 `false`，
`getCurrentlyCasting()` 恒返回 `null`，**不能用它兜底推断**清理时机。

## 4. 超限自动释放与手动释放的动作时钟

`ActionContainer` 内部按 `actualTick = currentTick - getCastTime(level)` 对 `trigger_rate` 取模。

**失效**：若让 DS 自己走到完成点，它会把**越限后的** `currentTick` 原样传给
`tickDefaultActions`。固定情景 `cast_time = 60`、`max_overcharged_duration = 20`、
`trigger_rate = 3`：自动释放时 `currentTick = 80`、`actualTick = 20`，
动作被取模跳过，却照样扣蓝、进冷却并触发连携——与手动松手的结果不一致。

**当前契约**：在完成点**前一步**接管，自动释放与手动释放走同一份结算代码。
默认动作必须收到 `castTime` 作为时钟起点，使 `actualTick` 从 0 开始。

## 5. 取消不能走 DS 原生停止流程

`currentTick` 越过 `castTime` 会让 `DragonAbilityInstance#isApplyingEffects()` 提前返回
`true`，进而使 `MagicData#stopCasting(player, instance)` 误判为"效果已生效"而**凭空施加冷却**。

**当前契约**：取消必须显式 `stopCasting(…, false)`，不能复用 DS 原生停止路径。

## 6. 维度绑定的服务端状态

**失效**：早期实现用 `static Map<ResourceKey<Level>, …>` 保存"按维度"的服务端视觉状态。
键是**维度键**而不是 `Level` 实例，因此换存档后仍然存活：
进入时间较大的存档 A、效果未结束时退出、再进入时间较小的存档 B，
`B.now - A.lastSentTick` 可能为**负数**，导致新效果长时间不发包，或旧到期时间污染新存档。

**当前契约**：所有"按维度"的服务端状态必须挂 `Level` 数据附件（`AAAttachments`），
随 `ServerLevel` 实例生灭。tick 路径用 `getExistingDataOrNull` 而非 `getData`，
避免给从未用过的维度创建默认值。

## 7. 屏幕视觉节流：租期与维度

**为什么要记"覆盖到什么时候"**：节流若只比较"参数有没有变"，会出现
"先发 1 刻、再在窗口内用同参数发 100 刻被丢弃"——短时长反而覆盖长时长。
因此记录客户端**已知**会持续到哪一刻（`coveredUntil`），
"延长租期"的请求必然放行。

**为什么每条槽还要记"属于哪个维度"**：`coveredUntil` 是绝对游戏刻。
玩家从时间较大的维度切到新维度后，旧维度的 `coveredUntil` 可能远大于新维度的当前时间，
且 `now - last.tick()` 可能为负数，导致新维度效果长时间不显示。

**当前契约**：状态按「玩家 + 视觉类型」分槽，每槽记录维度键，与本次不一致时整槽作废。

## 8. 方块震动：视觉可合并、声音必须按动作分组

**背景**：震动包按 `QuakeShape(height + duration + sound)` 跨施法者合并，
因此同参数的两批方块在协议与包数量上只算一份；而声音的声源取**该批方块的几何中心**，
音量固定 `1.0`（可听半径约 16 格）。

**失效**：若声音也按形状合并，同一玩家同一技能的两个独立动作
（例如两个领域同时结算，或 `max_domains > 1`）会在同一服务端刻被并成一组，
声源落在两片区域的**中间**，而两片区域都超出可听半径——结果是两边都听不到。

**当前契约**：
- 视觉包按形状跨施法者合并；
- 声音按「形状 + 施法者 + 技能 + **施法起点世界刻**」分离；
- 技能段取 `ResourceKey` 而非实例，使同一动作在 `trigger_rate` 内的重复触发仍只响一声。

**动作身份**取"施法起点世界刻"，与 `DomainTarget` / `DomainInstance` 判定"同一次施法"
用的是同一个量：`castStartTick = now - (currentTick - 1)`。
这在同一次施法内恒定、不同次施法必然不同，因此天然是动作身份，
不需要 DS 提供施法 ID（DS 也没有）。

**为什么用 ThreadLocal 作用域**：方块效果的形参由 DS 的
`AbilityBlockEffect#apply(dragon, ability, position, direction)` 固定，无法加参数。
在**派发点**设置作用域、在**效果内**读取，是唯一不改变接口的做法。
作用域按线程隔离，因此即便将来有别的线程意外读到，拿到的是 `null`
而不是别人的身份，退化为保守分组。

## 9. 领域：首轮立即执行与重入防护

**首轮**：若只依赖周期结算，`duration < apply_interval` 的组永远等不到第一次结算，
会彻底静默丢失。因此新加入的组在并入当下**立即执行一次首轮**，续帧不重复。

**重入三道防线**：
1. `effectSets` 遍历用 `List.copyOf` 快照；
2. `removed` 标志（`DomainData.remove` 先 `markRemoved` 再 `end`；tick 与 applySet 逐目标复查）；
3. `end` 的 `ended` 幂等闸门。

**注意**：快照只挡 `ConcurrentModificationException`，**不保证结算顺序**。
效果回调可以执行任意技能效果（含 `run_function`），因此回调里可能再次进入领域逻辑。

## 10. 未加载区块门控

方块筛选统一跳过未加载区块：条件上下文要读 `getBlockState`，
在未加载区块上求值会**同步加载或生成区块**，把一次技能扫描变成世界生成。

**当前契约**：方块分支一律跳过未加载区块，不因技能扫描而加载或生成区块。

## 11. 光束相交：六轴不够，必须用完整 SAT

**失效**：六轴分离轴检测（三个面法线 + 三个叉积轴）会漏掉真正的交点，
产生**假命中**——即"判定为相交、实际并不相交"。

**当前契约**：使用完整 SAT（补全 9 条叉积轴）。叉积轴显式列出而不是隐式枚举，
避免退化轴被静默跳过。

## 12. 放置确认的两阶段

**失效**：`BlockEvent.EntityPlaceEvent` 派发期间最终取消状态未知。
若在事件里直接触发技能，那么**被后续监听器取消的放置也会触发技能**。

**当前契约**：登记候选放置 → 等事件派发结束后 → 在下一个维度刻确认未取消才分发。
只响应最终未被取消的放置。

## 13. 附魔查询的线程契约

平台不保证每个事件回调都在主线程上。已知例外是 `GetEnchantmentLevelEvent` 与
`ItemTooltipEvent`：它们由调用点直接 post，而原版重建创造模式搜索索引时会在
`Worker-Main-*` 线程上问到它们。

**当前契约**："非主线程一律不结算"。
判定为不受支持的线程时静默返回空结果，既不遍历实体表也不读附件——
不抛异常，也不排队到主线程（事件要求当场返回）。
因此工作线程上查不到本模组附加的**临时**附魔等级，这是有意的降级。

**注意**：判定依据是"这个对象是不是服务端对象"（`ServerLevel` / `ServerPlayer`），
**不是**物理端。单人游戏里物理客户端同时跑着逻辑服务端。
连 `Worker-Main-*` 后台线程也会被误判成客户端，这正是需要区分逻辑端与执行线程的原因。

## 14. 附魔消费端的并发

`EnchantmentBonusThreads` 把"判定"与"消费"分开：判定是纯函数，
消费者只读取结论。判定收在 `EnchantmentBonusThreads`，其余调用点只消费它的结论。

## 15. 模糊后处理链的生命周期

**失效**：模糊链持有在旧 `ResourceProvider` 上编出来的着色器。
资源重载（F3+T / 换资源包）后旧链继续被使用，表现为 shader 报错持续存在，
"改好文件再重载"这条恢复路径失效。

**当前契约**：链的生命周期**外接**——客户端资源重载时作废当前链（下一次渲染按需重建），
游戏关闭时释放。

## 16. 只读快照 vs 活视图

**原则**：正式查询一律返回当刻定格的不可变结果（`DomainInfo` 是值对象）。

**例外的判据**是"调用频率与是否需要跨刻比较"：
- 低频查询 → 快照（如反伤条目的 `active`）；
- 逐帧渲染 → 活视图（如 `ClientBlockGlowState#entries()`，每帧遍历最多 4096 条，
  若改成逐帧拷贝等于用真实帧开销换渲染器并不需要的契约纯度）。

活视图路径必须在方法注释里标明为**内部渲染入口、不属于正式 API**。
